## 2-5. 공통 요구사항

| 항목 | 내용 | 완료 |
| --- | --- | --- |
| 3 Layer | Controller – Service – Repository 역할 분리 | |
| DTO 분리 | 요청·응답은 DTO, Entity를 그대로 응답하지 않음 | |
| Entity 설계 | 기본키 전략, `nullable = false`, `unique = true` | ✅ |
| 연관관계 | 4개 관계 `@ManyToOne` + 지연 로딩 | ✅ |
| JPA Auditing | BaseEntity로 생성·수정 시각 자동 기록 | ✅ |
| Query Methods | 아이디 중복 확인 ✅, 역할별 주문 목록 | |
| Validation | 요청 DTO 검증, 실패 시 400 | |
| Spring Security + JWT | 토큰 발급, 필터 검증, 역할별 접근 제한 | ✅ |
| RESTful URL | 자원은 명사, 행위는 HTTP 메서드 | |
| 상태 코드 | 201, 400, 403, 404 등 상황에 맞게 | |
| 비밀번호 | BCrypt, 평문 저장 금지 | ✅ |
| enum | `EnumType.STRING` | ✅ |

## 5-2. 코드 점검

| 항목 | 완료 |
| --- | --- |
| 연관관계 4개가 `@ManyToOne` + `FetchType.LAZY` | ✅ |
| BaseEntity(`@MappedSuperclass`) 상속, `@EnableJpaAuditing` 선언 | ✅ |
| 필수 컬럼 `nullable = false`, 아이디 `unique = true` | ✅ |
| enum은 `@Enumerated(EnumType.STRING)` | ✅ |
| Controller → Service → Repository (Controller가 Repository를 직접 호출하지 않음) | |
| 응답은 DTO, 응답 DTO에 비밀번호 필드 없음 | |
| 요청 DTO에 검증 어노테이션과 `@Valid` | |
| 아이디 중복 확인과 역할별 주문 목록을 Query Methods로 | |
| 메뉴 삭제가 실제 DELETE가 아닌 삭제 표시 | |
| 실제 비밀번호·JWT 비밀키를 GitHub에 올리지 않음 | |
