### [2026-10-07] 문서 위치: 기록 문서는 docs/, 루트 문서는 그대로

- **상황**: 설계 결정·트러블슈팅을 기록할 위치가 필요했다. 기존 md 파일(CLAUDE.md, HELP.md)도 함께 옮길지 고민했다.
- **선택지**
  - A. 모든 md 파일을 docs/로 모은다.
  - B. 작업하며 쌓이는 기록만 docs/에 두고, 루트 문서는 그대로 둔다.
- **결정**: B
- **이유**
  - CLAUDE.md는 루트에 있어야 Claude Code가 세션 시작 시 자동으로 읽는다.
  - README.md는 루트에 있어야 GitHub 저장소 첫 화면에 표시된다.
  - HELP.md는 Spring Initializr가 생성한 참고 링크 모음이고 .gitignore에 포함되어 있어 과제 문서가 아니다.
- **결과**: docs/decisions.md, docs/troubleshooting.md를 만들고, 이후 API 명세·ERD 등도 docs/에 추가한다.

### [2026-10-07] 테이블명: 복수형으로 통일

- **상황**: 엔티티 이름 그대로 `user`, `order` 테이블을 만들려 했으나, 둘 다 PostgreSQL 예약어라 그대로 쓸 수 없었다.
- **선택지**
  - A. 접두사를 붙인다. (`p_user`, `p_order`)
  - B. 복수형으로 바꾼다. (`users`, `orders`)
- **결정**: B
- **이유**
  - 예약어 문제가 자연스럽게 해결된다.
  - REST URL(`/api/users`, `/api/orders`)과 이름이 맞아 읽기 쉽다.
  - 접두사는 의미 없는 글자가 붙어 테이블명만 보고 뜻을 파악하기 어렵다.
- **결과**: 4개 테이블 모두 `users`, `menus`, `orders`, `payments`로 맞췄다. 엔티티 클래스명은 단수(`User`)로 두고 `@Table(name = "users")`로 지정한다.

### [2026-10-07] 아이디 길이 검증: DTO에서, DB는 상한만

- **상황**: 아이디는 4~20자라는 규칙이 있다. 이 검증을 DB와 코드 중 어디에 걸지 고민했다.
- **선택지**
  - A. DTO 검증(`@Size(min = 4, max = 20)`)만 하고, DB는 `varchar(20)`으로 상한만 건다.
  - B. A에 더해 DB에도 CHECK 제약(`char_length(username) BETWEEN 4 AND 20`)을 건다.
- **결정**: A
- **이유**
  - 길이 규칙은 바뀔 수 있는 비즈니스 규칙이라, DB에도 걸면 변경 시 코드와 DB를 둘 다 고쳐야 한다.
  - DB 제약에 걸리면 별도 처리 없이는 500으로 응답된다. 요구사항(400)을 맞추려면 어차피 DTO 검증이 먼저 걸러야 한다.
  - `ddl-auto: update`는 이미 만든 테이블에 CHECK 제약을 추가하지 않아 적용도 번거롭다.
- **결과**: DB는 `not null`, `unique`, `varchar(20)`까지만 두고, 4~20자 검증은 회원가입 요청 DTO에서 한다.

### [2026-10-07] 주문 총액: Service 계층에서 계산해 저장

- **상황**: 주문 총액(메뉴 가격 × 수량)을 누가, 어디서 계산할지 정해야 했다.
- **선택지**
  - A. 클라이언트가 계산한 금액을 요청으로 받아 저장한다.
  - B. DB에서 계산한다. (트리거로 `menus.price`를 읽어 `total_price`를 채우는 방식)
  - C. 저장하지 않고, 조회할 때마다 메뉴 가격 × 수량으로 계산한다.
  - D. 주문 생성 시 Service 계층에서 메뉴 가격을 조회해 계산하고 `total_price`에 저장한다.
- **결정**: D
- **이유**
  - A는 요청 본문의 금액을 조작하면 만 원짜리 주문을 백 원에 결제할 수 있다.
  - B는 PostgreSQL의 계산 컬럼(generated column)이 같은 행의 값만 참조할 수 있어서, 다른 테이블의 메뉴 가격을 쓰려면 트리거가 필요하다. 트리거는 Java 코드에서 보이지 않아 로직을 추적하기 어렵고, 테스트도 DB 없이는 할 수 없다.
  - C는 사장님이 메뉴 가격을 바꾸면 이미 끝난 주문의 총액까지 바뀐다.
  - D는 금액 계산이라는 비즈니스 규칙이 Service 한곳에 모여 읽기 쉽고, 할인·배달비 같은 규칙이 추가돼도 코드만 고치면 된다. DB 없이 단위 테스트도 할 수 있다.
- **결과**: 주문 요청 DTO에는 메뉴 ID·수량·주소만 받는다. 저장된 `total_price`는 주문 당시 금액으로 남고, 결제 금액(`amount`)도 이 값을 복사한다. 비즈니스 규칙은 DB가 아니라 Service에 둔다는 원칙은 이후 상태 전이 검증 등에도 동일하게 적용한다.

### [2026-10-07] 결제 수단: CARD만 정의

- **상황**: 결제 수단 enum에 어떤 값을 둘지 고민했다. 처음에는 확장을 생각해 `CASH`도 넣었다.
- **선택지**
  - A. 앞으로 쓸 수 있는 값(`CASH` 등)을 미리 넣어둔다.
  - B. 요구사항에 있는 `CARD`만 둔다.
- **결정**: B
- **이유**
  - 요구사항이 카드만 허용하고, 그 외 값은 400으로 거절해야 한다.
  - A로 하면 DB는 `CASH`를 받아주는데 코드에서 따로 막아야 해서, 허용 범위가 두 곳에서 어긋난다.
  - 값 추가는 필요해질 때 enum에 한 줄 넣으면 된다.
- **결과**: `PaymentMethod`는 `CARD` 하나. enum 값을 나중에 추가할 때는 Hibernate가 만든 CHECK 제약이 `ddl-auto: update`로는 갱신되지 않는다는 점에 주의한다.
