### D-01. 문서 위치: 기록만 docs/, 루트 문서는 그대로
`채택` · 2026-10-07

- **고민**: 모든 md를 docs/로 모을지, 작업 기록만 docs/에 둘지
- **결정**: 작업 기록만 docs/에 둔다.
- **이유**
  - CLAUDE.md는 루트에 있어야 Claude Code가 자동으로 읽는다.
  - README.md는 루트에 있어야 GitHub 첫 화면에 표시된다.

### D-02. 테이블명: 복수형으로 통일
`채택` · 2026-10-07

- **고민**: `user`, `order`가 PostgreSQL 예약어라 접두사(`p_user`)와 복수형(`users`) 중 선택
- **결정**: 복수형 (`users`, `menus`, `orders`, `payments`)
- **이유**
  - REST URL(`/api/users`)과 이름이 일치한다.
  - 접두사는 의미 없는 글자라 테이블명만 보고 뜻을 알기 어렵다.

### D-03. 아이디 길이 검증: DTO에서, DB는 상한만
`채택` · 2026-10-07

- **고민**: 4~20자 검증을 DTO에만 둘지, DB CHECK 제약까지 걸지
- **결정**: DTO(`@Size`) 검증 + DB는 `varchar(20)`
- **이유**
  - 바뀔 수 있는 비즈니스 규칙이라, DB에도 걸면 변경 시 두 곳을 고쳐야 한다.
  - DB 제약에 걸리면 500이 나므로, 400 응답을 위해 어차피 DTO 검증이 필요하다.

### D-04. 주문 총액: Service에서 계산해 저장
`채택` · 2026-10-07

- **고민**: 클라이언트 전달(A) / DB 트리거(B) / 조회 시마다 계산(C) / Service에서 계산 후 저장(D)
- **결정**: D
- **이유**
  - A는 금액 조작이 가능하다.
  - B는 다른 테이블 값을 쓰려면 트리거가 필요해 로직이 코드 밖으로 숨는다.
  - C는 메뉴 가격이 바뀌면 지난 주문의 총액까지 바뀐다.
- **원칙**: 비즈니스 규칙은 DB가 아니라 Service에 둔다. (상태 전이 검증에도 동일 적용)

### D-05. 결제 수단: CARD만 정의
`채택` · 2026-10-07

- **고민**: 확장을 대비해 `CASH`도 넣을지
- **결정**: `CARD`만
- **이유**
  - 요구사항이 카드만 허용한다. 미리 넣으면 DB는 받고 코드에서 막아야 해 허용 범위가 어긋난다.
- **주의**: enum 값 추가 시 `ddl-auto: update`는 CHECK 제약을 갱신하지 않는다.

### D-06. JPA Auditing 선언 위치: 메인 클래스
`채택` · 2026-10-07

- **고민**: `@EnableJpaAuditing`을 메인 클래스에 둘지, 별도 설정 클래스(`global/config`)로 뺄지
- **결정**: 메인 클래스(`DeliveryApplication`)에 선언
- **이유**
  - 설정 클래스 분리는 `@WebMvcTest`에서 생길 수 있는 에러를 미리 피하기 위한 것인데, 아직 그런 테스트가 없다.
  - 겪지 않은 문제를 위해 구조를 먼저 늘리기보다, 실제로 문제가 생겼을 때 원인을 확인하고 고치는 쪽을 택했다.
- **재검토**: `@WebMvcTest` 작성 시 `JPA metamodel must not be empty` 에러가 나면 별도 설정 클래스로 분리하고, 원인을 troubleshooting에 기록한 뒤 이 항목을 `대체됨`으로 바꾼다.

### D-07. 주문 총액: Order 엔티티 생성 시 계산
`채택` · 2026-10-07

- **고민**: D-04에서 서버가 계산하기로 했지만, 계산 위치를 Service와 Order 엔티티 중 어디에 둘지 엔티티 구현 중 다시 고민했다.
- **결정**: Order 생성자에서 `menu.getPrice() * quantity`로 계산한다.
- **이유**
  - 총액을 밖에서 넘겨받지 않으므로, 잘못된 총액을 가진 Order가 만들어질 수 없다.
  - "총액 = 가격 × 수량"은 주문 자체의 규칙이라 Order 안에 두는 것이 자연스럽다.
  - DB나 Service 없이 `new Order(...)`만으로 계산을 테스트할 수 있다.
- **유지**: D-04의 핵심(클라이언트 금액을 받지 않고, 서버가 DB의 메뉴 가격으로 계산해 주문 시점 값을 저장)은 그대로다.
- **재검토**: 쿠폰·배달비처럼 계산에 다른 Repository나 외부 정보가 필요해지면 Service에서 계산하는 방식으로 다시 검토한다.
- **변경**: `erd.md` 테이블 명세서의 `total_price` 설명을 "주문 생성 시 Service에서 계산" → "주문 생성 시 Order 엔티티에서 계산"으로 수정했다.

### D-08. PasswordEncoder를 별도 설정 클래스로 분리
`채택` · 2026-10-07

- **고민**: `PasswordEncoder` 빈을 `SecurityConfig` 안에 둘지, `PasswordConfig`로 뺄지
- **결정**: `global/config/PasswordConfig`에 두고, 반환 타입은 인터페이스(`PasswordEncoder`)로 한다.
- **이유**
  - 이후 `SecurityConfig`가 JWT 필터를, 필터가 회원 조회를, 회원 쪽이 `PasswordEncoder`를 필요로 하면 순환 참조가 생길 수 있다.
  - `SecurityConfig`는 요청 허용·차단 규칙, `PasswordEncoder`는 회원가입·로그인 로직에서 쓰는 도구로 역할이 다르다.
  - 반환 타입을 인터페이스로 두면 암호화 방식을 바꿀 때 이 한 줄만 고치면 된다.

### D-09. JWT subject: 회원 번호 대신 아이디(username)
`채택` · 2026-10-08

- **고민**: 토큰의 `sub`(누구의 토큰인지)에 회원 번호(`userId`)와 아이디(`username`) 중 무엇을 넣을지, 발급 시각(`iat`)을 제거할지
- **결정**: `sub`에 `username`을 넣고, 역할은 `role` claim에 enum 이름(`"OWNER"`)으로 넣는다. 발제의 필수 항목(아이디, 역할, 만료 시간) 외에 표준 claim인 발급 시각(`iat`)도 함께 담는다.
- **이유**
  - 발제가 "토큰에는 아이디와 역할, 만료 시간을 담는다"고 정하고 있고, 발제 전체에서 "아이디"는 중복 불가인 로그인 아이디(`username`)를 뜻한다.
  - `username`도 unique 제약이 있어 사용자를 하나로 특정할 수 있다. 메뉴·주문에 주인을 연결할 때 어차피 `User`를 조회해야 하므로, `findById` 대신 `findByUsername`을 써도 조회 횟수는 같다.
  - `userId`를 고른다면 내세울 수 있는 장점(아이디 변경에 강함)은 이 과제에 없는 기능을 위한 대비다. D-06과 같은 원칙으로, 겪지 않은 문제를 위해 요구사항에서 벗어나지 않는다.
  - `iat`는 민감정보가 아니고, 디코딩했을 때 발급 시각과 유효 기간(`exp - iat`)을 바로 확인할 수 있어 디버깅에 도움이 된다.
- **검토한 대안**: `sub`는 `userId`로 두고 `username` claim을 추가(발제는 만족하지만 지금 쓸 곳 없는 값이 늘어남)
- **재검토**: 아이디 변경 기능이 생기거나, 매 요청마다 PK가 필요해지면 `userId`를 claim에 추가하는 방식을 검토한다.
